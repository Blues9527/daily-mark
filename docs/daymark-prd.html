01 / COMPETITIVE RESEARCH

竞品都在解决「排得下」，
很少解决「排得准」。

调研了 6 款时间块 / 清单 / AI 日历产品，以及国内清单系产品的共性。结论很一致：市场不缺清单和日历，缺的是对「今天到底能完成什么」的现实判断，以及计划与实际的闭环。

Sunsama美国 · 订阅约 $20/月

把任务、日历、每日规划仪式和日终 shutdown 串成一套工作流，主张「从容开始、专注、安心结束」。

值得借鉴每日规划仪式、Focus Mode、日终 highlights、日历与任务统一。
缺口围绕打工人和会议日历设计，价格高，移动端不是主角。
Motion美国 · 订阅约 $29/月

AI 自动排程的代表：任务和项目自动找时间，冲突时自动重排，偏团队与项目管理。

值得借鉴自动排程、冲突重排、把「排不下」变成系统问题。
缺口黑盒感强、学习成本高；对个人创作者的精力节奏不敏感。
Reclaim.ai美国 · 免费起 / 约 $10/月

在 Google / Outlook 日历上自动防守 Focus Time、Habits、Buffer，把「保护时间」做成 AI agent。

值得借鉴缓冲时间、自动防守、按目标倒推时间块。
缺口依赖外部日历；偏「防守已有时间」，而非「规划今天怎么过」。
Structured德国 · 约 $3/月或买断

单日时间轴可视化的标杆，快速创建任务、跨手机/桌面/手表，15M+ 下载、400K+ 五星。

值得借鉴极低摩擦的视觉排程、时间轴本身就是产品、价格友好。
缺口纯手动，没有容量预警、没有执行数据、也没有复盘。
TickTick / 滴答清单中国 · 约 ¥139/年

清单、日历、番茄、习惯、统计的全能型选手，NLP 输入和跨端体验成熟。

值得借鉴快速捕捉、自然语言时间识别、低门槛上手。
缺口功能堆叠；时间块不是主角，「今天是否排得下」不清晰。

01

头部产品都在拼「工作流」，但默认你是开会的人。 Sunsama / Motion / Reclaim 都从日历空隙出发；自由职业者的日历往往很空，真正稀缺的是精力与边界。

02

移动端时间轴大多只能「看」，不能「排」。 拖拽在小屏上依然别扭。点选时段 + 智能建议，比精确拖拽更适合小程序。

03

自动排程解决「排得下」，但会制造失控感。 黑盒重排让人不知道计划为什么变了。「建议 + 一键接受 + 单块可改」是更稳的折中。

04

复盘普遍是报表，不是闭环。 用户不需要更多图表，需要「为什么偏了、明天怎么改」。归因 + 明日容量建议是空位。

05

中文产品强在清单、番茄、打卡，弱在现实容量。 用户被教育了「记录」，但没有被教会「估算」。容量模型是可以建立差异化的地方。

02 / USER & PROBLEM

不是没有计划，
是每次都排得太满。

自由职业者的时间看起来自由，实际被需求、修改、消息和自我期待切碎。产品要解决的不是「记录更多」，而是「当天做得完，并且知道为什么没做完」。

林一29 岁
自由插画师 / 独立接单 · 一人公司 · 微信里全是需求
  • 8:30送完孩子，咖啡还没喝完，先刷一遍微信。
  • 9:10想画主视觉，又想起报价没回、发票没开。
  • 10:40客户临时改需求，上午的深度块被切掉一半。
  • 15:00清单越写越长，干脆先做杂事。
  • 23:00发现正事没做完，明天继续排满。

「我不是没计划，是每次都排太满，然后一整天都在还债。」

合成画像，基于公开创作者社区讨论与竞品评论归纳；上线前需 5 人日记研究验证

核心 JTBD

当我早上只有十分钟规划时，我想快速判断「今天到底能完成什么」，并把最重要的事放进我状态最好的时段；这样我晚上不会因为没做完而自责，第二天也愿意继续打开它。

使用场景

晨间 90 秒规划 · 白天被临时需求打断后的重排 · 开始深度创作前的专注启动 · 晚间 60 秒对账 · 周日的下一周节奏预览。

产品承诺

不替你决定人生，只帮你看清今天。计划可以崩，但每次崩都能在两步内重排；留白不是浪费，是明天还能继续的前提。

非目标用户（MVP）

需要团队排期、甘特图、工时审批的项目经理；只想做习惯打卡的用户；需要强制锁机的极简番茄用户。

03 / POSITIONING

先算容量，再排时间块，
晚上自动对账。

一句话定位：给自由职业者的日内规划器。不是又一个待办清单，而是一张每天都能被验证的「时间预算表」。

PRODUCT POSITIONING

给自由职业者与创作者的日内规划器：用容量约束让计划变现实，用时间块让执行变简单，用日终对账让明天更准。

不是 另一个全能清单
另一个自动排程黑盒
另一个番茄打卡器
原则 01

容量先于清单

没有容量约束的计划只是愿望。先看今天有多少可用小时、多少高质量精力，再决定放什么进去。

原则 02

留白是功能

默认只排 60–70% 的可用时间，并保护缓冲。留白不是浪费，是应对临时需求与状态波动的空间。

原则 03

不羞辱中断

没完成不是失败，是可以被重排的事实。任何一次偏航都能在两步内处理，不靠自责驱动。

MVP 不做：社交动态与排行榜 · 团队协作与共享日历 · 甘特图/项目依赖 · 强制锁机与惩罚式打卡 · 复杂 OKR 体系。先把「今天」做透，再谈「一周」和「一年」。

05 / CORE FLOWS

四个流程，覆盖一天里
最重要的四个时刻。

规划要快，执行要静，复盘要短，崩了要能救。所有流程都围绕一个原则：减少决策，不减少掌控感。

晨间 · 90 秒规划

触发：首次打开 / 08:30 提醒
  1. 打开今日页，先看到「可用 6.0h / 已排 0h」与昨天的兑现率。
  2. 清空大脑：快速记录 5–10 条，不排序，默认时长 30 分钟。
  3. 只留三件：超过 3 件自动进入「本周稍后」，不做二次确认。
  4. 智能排一版，按精力把深度创作放进上午；接受后可单块调整。
  5. 生成今日计划，同时保留 20% 缓冲。完成时间目标 ≤ 90 秒。

日内 · 只面对当前块

触发：时间块开始 / 手动进入
  1. 今日页只强调当前块；其他块降低对比度，避免提前焦虑。
  2. 点播放进入专注模式，倒计时与计划时长一致，可暂停。
  3. 走神时用「走神捕手」记录想法/待办/情绪，不离开当前任务。
  4. 完成后自动记账；没完成则选择剩余时长，系统寻找最近空位。
  5. 顺延不会挤压留白；如果会，先提示「今天要牺牲留白吗」。

晚间 · 60 秒对账

触发：最后一个块结束 / 21:00
  1. 自动对比计划与实际，展示兑现率、完成数、实际专注时长。
  2. 点选偏航原因（最多 2 个），不做强制长文本。
  3. 系统给出明日容量建议，默认降低 0.5–1h，可一键接受。
  4. 写一句「值得保留的事」，保存后结束，不生成公开内容。
  5. 连续记录 +1；即使只完成 1 件，也保留记录。

异常 · 计划崩了怎么办

触发：块超时 / 临时需求
  1. 当前块显示「已超时 18 分钟」，提供「再给 15 分钟 / 记下剩余 / 放弃」。
  2. 选择剩余时长后，系统在接下来 48 小时内找最近空位。
  3. 重排结果先预览：哪些块移动、留白是否被占用、哪些进明天。
  4. 一键接受或只接受部分；被移动的块标注「因客户需求调整」。
  5. 不扣连续记录，不出现「失败」「懒惰」等评价性文案。

关键规则

  • 容量公式：可用分钟 − 固定事项 − 20% 缓冲；缓冲可下调，但建议不低于 10%。
  • 状态机：inbox → planned → active → done / partial / moved；任何状态都能回到 inbox，不产生不可逆操作。
  • 重排约束：不覆盖 locked 块；不主动占用留白；跨天移动必须预览并由用户确认。
  • 记账口径：实际时长取「计时器记录」与「用户确认」的较大值，避免漏记；部分完成保留剩余分钟。
  • 留白保护：buffer / rest 块不参与智能排程占用；任何占用都必须由用户显式确认。
  • 数据同步：本地优先、云端合并，按 updatedAt 解决冲突；离线可记录，联网后补同步。
  • 多端预留：Block 使用绝对日期与分钟，避免时区与跨天歧义；为 P2 日历同步预留 externalId。

07 / ROADMAP & RISKS

先用 6 周验证一件事：
用户愿不愿意被容量约束。

最大风险不是做不出功能，而是用户觉得「预估时长」太麻烦。所以第一阶段必须验证这件事，再谈智能与增长。

W1–2 · 验证

日记研究 + 纸原型

找 5 位自由职业者，记录一周真实计划与实际；验证容量、三件事、归因标签是否被理解。

W3–6 · MVP

七件事闭环

收集箱、容量、三件事、时间轴、专注、重排、日终复盘。微信小程序单端，先不做日历导入。

W7–10 · 内测

30 人 + 数据校准

看规划完成率、计划兑现率、次日回访；每周迭代文案与默认值，不新增功能。

P1 · 增强

建议与节奏

明日容量建议、走神捕手、连续记录、周报、订阅提醒、模板日。验证付费意愿。

主要风险与应对

  • 用户不愿预估时长。 默认时长 + 历史学习 + 只要求「短/中/长」三档，首次不强迫精确。
  • 容量模型被感知为说教。 文案只描述事实与出口，不评价自律；留白始终可见且可保护。
  • 小程序时间轴操作摩擦。 首选点选时段与智能建议；拖拽仅作为增强，不设为唯一路径。
  • 提醒造成压力。 默认每日 ≤3 条，允许「今天不提醒」；不做连续打卡惩罚。
  • 数据隐私顾虑。 复盘默认私密；不读取聊天内容；导出与删除入口前置。

待确认的开放问题

  1. MVP 是否直接用「点选时段」替代长按拖拽，降低开发与学习成本？
  2. 日历导入是否进 P0？微信生态内固定事项可能先靠手动录入。
  3. 免费与订阅的边界：容量、规划、复盘免费；智能排程与周报订阅？
  4. 是否做微信状态 / 小组件，让「当前块」在 App 外也能被看见？
  5. 连续记录是否允许无限补记？补记太多会让激励失真。

下一步建议：先约 5 位目标用户做一周日记研究；用这份原型做 30 分钟走查，重点观察他们是否理解「容量」与「留白」；再决定 MVP 是否保留智能排程。
